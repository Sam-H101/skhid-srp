# The server's game data from the players' `resources.db`

> **Version scope: 0.26g.** Written 2026-10-15 with the change that made srp
> read its game data at start instead of compiling it in.

## What and why

srp knew the game's data from tables compiled in: `item_params`, `maps` and
`modifications` generated by `scripts/gen-data-026g/*.py`, and nine
`gameplay/` files copied into `resources/binary-config-examples/*_026g`. A
release that adds items (the Duty exoskeleton 1805 and the Bandit balaclava
1810, the first) changes the players' `resources.db`, and the server must
then know exactly what the players have: the client crashes on a dictionary
or modification id it lacks (`lobby.md` §2.6), and an item the server does not
know cannot be sold, dropped or worn.

So the server's data is made from the very archive the players run, with
each release, and the server checks that it is: one source, the players'
files, and no copy of the 6.3 GB archive on the server.

## The server's game data of a release

`srp-game-data extract` (`crates/resources-db`, `server`) makes it, where
0.26g's `resources.db` is (the release machine); `make_client_026g.py` runs
it for every ZIP that changes `resources.db`, writing `server-game-data.db`
beside the ZIP.

1. It opens 0.26g's archive (6 285 533 906 bytes) with the plan of the
   players' ZIP laid over it in memory (`resources_db::plan`), as the
   players' updater lays it: every size and checksum checked first (the
   installed file's size, the original of each range a region replaces,
   each blob). The plan is read by the updater's own code
   (`client/updater/logic`). So the file table read is the players', checked
   by the plan's sha256.
2. It takes the files srp reads: every file under `gameplay/` (510 in the
   candidate release) and each project's `client_project` (73; kept empty,
   srp only asks whether a project is there). Each is checked against that
   table: its size, and the table's checksum of its bytes, the engine's
   CRC-32 (`boost::crc_optimal<32, 0x04C11DB7>`, reflected input, output not
   reflected, no final xor), which 0.26g's archive and the porter's releases
   have right for every file (checked on all 583).
3. It adds `srp/provenance`: the format, the sha256 of the ZIP's plan file,
   and the plan's lines for `game/resources.db` (with the installed size,
   each replaced range's original sha256 and each blob's), or `plan none`.
4. It writes them as an archive of their own (`resources_db::write`: the
   format the reader reads; mount root, folders and files in name order, each
   file's bytes once, the CRC-32; the same inputs give the same bytes).

The candidate release gives 2 856 185 bytes, sha256 `ecc419ff…337c`, in 0.9 s,
the same bytes every time.

## How srp reads it

`SRP_GAME_DATA` names the file; `SRP_DOWNLOAD_FILE` is the ZIP the web server
hands out. At start, before anything else, srp:

1. reads the plan of that ZIP and the data's `srp/provenance`, and refuses to
   start unless the data was made for that plan: a ZIP without its data, or
   data without its ZIP, stops it with a message naming both plans and the
   command that makes the right data;
2. reads every `gameplay/` file and the projects (`game_data::GameData`);
3. builds every table from them and checks one file against another
   (`tables::check`): each item's config is there, each default
   modification exists, ids once.

The tables are then built from those files when first used. It needs
neither 0.26g's archive nor the blobs.

## Questions answered

1. **Which reader.** `crates/resources-db`, taken from resource-porter's
   `deps/vostok-resources-db` (`src/fat.rs` at resource-porter 5d3b53e; the
   code began as github.com/srp-survarium/vostok-resources-db). Reading, the
   plan, a minimal writer of its own (after the porter's `pack.rs`), and the
   extraction; every offset is bounds-checked (a damaged table is an error,
   never a panic: a test flips every byte of a table), and the node kinds
   0.26g's archive has none of are refused by name. The workspace's unused
   git dependency on the porter's crate became the in-tree crate.
2. **How entries are stored.** Uncompressed, at an absolute offset, with the
   size and the CRC-32 in the node. 0.26g's archive has no compressed (PPMd)
   or inlined files, no soft links, erased nodes or external tables; it has
   hard links, to files and to 58 folders (1 030 of its 79 933 files are
   reached through those), which the reader resolves.
3. **Start-up cost.** The data's table and 4 MB of `gameplay/`: milliseconds.
   The extraction on the release machine: under a second.
4. **The compiled tables: dropped.** One path: tests and tools read
   `resources/game-026g/players.db`, which is exactly the extraction's
   output for the candidate release (an ignored test makes it again from
   0.26g's archive and the candidate ZIP and compares the bytes). Before the
   generated tables went, the derived ones were compared with them on
   0.26g's own archive with no plan: the 384 item rows and the carry limits,
   the 160 modification rows, the 79 map rows (`has_project` too) were equal
   row for row, and the nine copied files were byte for byte the archive's.
5. **What changed for the users of the tables.** `Dictionary`,
   `Modifications`, `Drops`, `Quests`, `SkillsTree`, `Awards` and `Loadouts`
   parse the players' file at their `PATH` instead of an embedded copy;
   `item_params::all`, `modifications::all_item_mods` and `maps::all` are
   derived (`derive`) where `ITEM_PARAMS`, `ITEM_MODS` and `MAP_MODES` were;
   `item_params::player()` is what the five carry constants were;
   `ItemParams::covered_slots` is new (`data.additional_model_slots`).
6. **Maps' level files.** Not read. A game mode needs its config and whether
   the archive has its project; a project's respawn points and a battery
   container's team are still in code (`match_msgs::rules`), by level, as
   they were.
7. **The live host.** `server-game-data.db` in the download folder beside the
   ZIP (`/opt/srp-026g/download/`, mounted already), `SRP_GAME_DATA` set by
   the compose file. The image build needs `client/updater/logic` beside
   `srp-026g` (or `SRP26_UPDATER_LOGIC` naming a copy) and Docker Compose's
   `additional_contexts` (2.17 or newer). `DEPLOY.md`, "The game's files".

## What stays in code

What the game's files do not say: the shop's exceptions (`prices::EXCEPTIONS`,
by item name; the balaclava has none and goes by the rule), the
bundles, a project's respawn points and container teams, the loadouts of new
accounts.

## A fix that came with it

An item's covered slots come from its own config for every item, and the
server now never lets anything be worn in a slot another worn item covers
(`session::v026g::rules`). 0.26g's four helmets with a built-in mask
(`blackmarket_helmet_5`, `renesanse_helmet_4`, `renesanse_helmet_6`,
`edge_helmet_6`) say they replace the mask's model, and the client's
paperdoll locks the mask's cell for them, but srp let a mask be worn under
them. Kits saved that way are mended when the accounts load, and such a kit
never plays.
