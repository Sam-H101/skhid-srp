# The server's game data from `resources.db` and its patches

> **Version scope: 0.26g.** Written 2026-10-15 with the change that made srp
> read its game data at start instead of compiling it in; made over
> 2026-10-16 for the patches the game mounts over `resources.db` (client
> patch revision 14).

## What and why

srp knew the game's data from tables compiled in: `item_params`, `maps` and
`modifications` generated by `scripts/gen-data-026g/*.py`, and nine
`gameplay/` files copied into `resources/binary-config-examples/*_026g`. New
content (an item, a map) reaches the players as a patch of `resources.db`:
the game mounts the stock archive and every `resources.db.patch_<n>` beside
it over it (n = 1 to 255 ascending, a later file over an earlier one), and
the players' updater keeps those files the ones the server lists (`GET
/patches`). The server must then know exactly what the players mount: the
client crashes on a dictionary or modification id it lacks (`lobby.md`
§2.6), and an item the server does not know cannot be sold, dropped or worn.

So the server's data is made of the very archives the players mount, and
the list the players' updater gets is the list of those archives: one
source, and no copy of the 6.3 GB archive on the server.

## The server's game data

`srp-game-data build` (`crates/resources-db`, `server`;
`crates/resources-db/README.md`) makes it where the archives are (the
release machine):

1. It lays the patches over `resources.db` in the game's order
   (`resources_db::overlay`), reading only their tables.
2. It takes the files srp reads: every file under `gameplay/` and each
   project's `client_project` (kept empty, srp only asks whether a project
   is there), each from the archive whose file the game sees, and checks it
   against that archive's table: its size, and the engine's CRC-32 of its
   bytes.
3. It adds `srp/provenance` (`skhid server game data 2`): `resources.db`
   (its name, size, sha256), and each patch with its name, size, sha256 and
   the URL the players' updater downloads it from.
4. It writes them as an archive of the game's own format
   (`resources_db::write`; the same inputs give the same bytes).

0.26g with the test patches 14, 15 and 16 gives 2 845 784 bytes (509
`gameplay/` files, 73 projects) in about 5 s; that is the test data,
`resources/game-026g/server-game-data.db`.

## How srp reads it

`SRP_GAME_DATA` names the file (the compose file: `download/server-game-data.db`).
At start, before anything else, srp (`game_data::init`):

1. opens it and checks every file against its table and reads the
   provenance (`resources_db::server::read`); a missing variable, a missing
   or damaged file, or a file without the provenance of this format stops it
   with a message that says how to make the data;
2. reads every `gameplay/` file and the projects (`game_data::GameData`);
3. builds every table from them and checks one file against another
   (`tables::check`): each item's config is there, each default
   modification exists, ids once.

The tables are then built from those files when first used. The web page
answers `GET /patches` with the provenance's patches (`Provenance::offered`,
`web_server::OfferedPatch`), in the game's order, `{}` for none: the players
fetch exactly the patches the server runs on. srp needs neither the archives
nor the patch files; those are at their URLs.

## Questions answered

1. **Which reader.** `crates/resources-db`, taken from resource-porter's
   `deps/vostok-resources-db` (`src/fat.rs` at resource-porter 5d3b53e).
   Every offset is bounds-checked (a damaged table is an error, never a
   panic), and the node kinds 0.26g's archive has none of are refused by
   name.
2. **Start-up cost.** The data's table and 4 MB of `gameplay/`:
   milliseconds.
3. **The compiled tables: dropped.** Tests and tools read
   `resources/game-026g/server-game-data.db` (an ignored test makes it again
   from 0.26g's archive and the test patches and compares the bytes, and
   checks that 0.26g's archive alone gives the same tables but for the
   patches' items). Before the generated tables went, the derived ones were
   compared with them on 0.26g's own archive: the 384 item rows and the
   carry limits, the 160 modification rows, the 79 map rows (`has_project`
   too) were equal row for row, and the nine copied files were byte for
   byte the archive's.
4. **What changed for the users of the tables.** `Dictionary`,
   `Modifications`, `Drops`, `Quests`, `SkillsTree`, `Awards` and `Loadouts`
   parse the game's file at their `PATH` instead of an embedded copy;
   `item_params::all`, `modifications::all_item_mods` and `maps::all` are
   derived (`derive`) where `ITEM_PARAMS`, `ITEM_MODS` and `MAP_MODES` were;
   `item_params::player()` is what the five carry constants were;
   `ItemParams::covered_slots` is new (`data.additional_model_slots`).
5. **Maps' level files.** Not read. A game mode needs its config and whether
   the archive has its project; a project's respawn points and a battery
   container's team are still in code (`match_msgs::rules`), by level.
6. **The live host.** `server-game-data.db` in the download folder
   (`/opt/srp-026g/download/`, mounted already), `SRP_GAME_DATA` set by the
   compose file. A release puts the patch at its URL, replaces the file and
   restarts srp (`DEPLOY.md`, "The game's files").

## What stays in code

What the game's files do not say: the shop's exceptions (`prices::EXCEPTIONS`,
by item name; the Bandit balaclava and the Duty exoskeleton have none and go
by the rule: Black Market's balaclava of item level 8 at rank 5, its last;
Renaissance's exoskeleton of level 15 at rank 10), the bundles, a project's
respawn points and container teams, the loadouts of new accounts.

## A fix that came with it

An item's covered slots come from its own config for every item, and the
server now never lets anything be worn in a slot another worn item covers
(`session::v026g::rules`). 0.26g's four helmets with a built-in mask
(`blackmarket_helmet_5`, `renesanse_helmet_4`, `renesanse_helmet_6`,
`edge_helmet_6`) say they replace the mask's model, and the client's
paperdoll locks the mask's cell for them, but srp let a mask be worn under
them; the Duty exoskeleton, worn in the back slot, covers the six other
armour slots. Kits saved that way are mended when the accounts load, and
such a kit never plays. The tests use the helmets and the balaclava of the
test data, and a stand-in suit for the six slots (the exoskeleton is not in
the test patches).
